# 词库与拼音索引升级方案

> 目标：让整句解码和编码候选能覆盖日常输入，而不是只依赖 20 万词的内置子集。
>
> **执行状态（2026-10-20）：Phase 1 已完成。** 构建工具已参数化，A/B/D/E 四档
> bin 已产出并通过结构与注音验证。实测数据、体积与 APK 影响见
> [`lexicon-build/REPORT.md`](lexicon-build/REPORT.md)。下文二、三节中的体积数字
> 为事前估算，以 REPORT 中的实测值为准。

## 一、先把东西认清楚

| 你给的文件 | 实际是什么 | 与本项目的关系 |
|---|---|---|
| `cn_dicts/*.dict.yaml`（base / ext / tencent / 8105 / 41448 / others） | [rime-ice](https://github.com/iDvel/rime-ice) 的 Rime 词库，GPL-3.0 | 本项目**只用了 8105 全量 + base 前 20 万** |
| `wanxiang-lts-zh-hans.gram`（398MB） | 文件头 `Rime::Grammar/1.0`，万象拼音的 Rime 语法模型（KenLM 系） | 构建时被 mmap，只为 6 万个种子词抽取转移对 |
| [metasequoiaime/chinese-ime-lm](https://github.com/metasequoiaime/chinese-ime-lm) | **候选重排器**仓库：KenLM 路线 + 字符级 Transformer 重排（4.5MB / 25.5MB，权重 Apache-2.0） | **不是你现在跑的引擎**，也没有被集成 |

结论：你现在缺的不是"换引擎"，是**词条没进全、拼音索引太窄、无注音词没处理**。`.gram` 已经在用，不用动。

## 二、当前实现与差距（实测数据）

### 2.1 现有构建

`tools/build_embedded_data.cpp`：

- 输入：`8105.dict.yaml` 全量 + `base.dict.yaml` 按词频截断到 20 万条
- 产出：207,622 词 / 226,448 个拼音键，`xy_embedded.bin` 15.5MB
- 索引：**整串全拼精确匹配**；简拼只给前 2.5 万个双字词生成；每键最多 12 个候选
- 字表：41448（4.6 万字，含生僻字）、others（容错读音）**完全没用**

### 2.2 你给的词库规模

| 文件 | 行数 | 带注音 | 说明 |
|---|---:|---:|---|
| base | 543,118 | 全部 | 真实词频，最大 |
| ext | 339,186 | 全部 | 三字及以上，与 base 不重复 |
| tencent | 981,543 | **无** | `columns: text, weight`，权重全是 100 |
| 8105 | 8,757 | 全部 | 通用规范汉字表 |

## 三、方案（推荐：分层构建 + 注音增强 + 索引增强）

### Phase 0：先定三个决策项

1. **体积档**：精简 A / 标准 B / 全量 E。
2. **是否公开发布**：rime-ice 是 **GPL-3.0**。内嵌其词库再分发，整个分发包要按 GPL-3 提供源码；这与"核心代码放 C++ 防逆向"直接冲突。私有自用无此问题。可选规避：不内置词库，改为用户自行导入（见 Phase 3）。
3. **是否要神经重排**：不建议现在做。metasequoia 自己的评测也承认重排只对"解码器拼出来、缺少词频证据"的候选有效；当前引擎的候选大多带词频，收益有限，且要引入推理运行时。

### Phase 1：重写构建工具（1～2 天，风险低）

把 `tools/build_embedded_data.cpp` 从"一次性脚本"改成可复用工具：

- 去掉 `/home/king/下载/...` 硬编码，改为命令行参数：
  `--dict-dir <目录> --profile core|standard|full --out <bin> --stats`
- 五库合并策略：
  - 同一 `(词, 拼音)` 取最大权重
  - base/ext 的权重原样保留（真实词频）
  - tencent/others 的 100 权重单独标记为"弱先验"，排序时永远排在真实词频之后
- **自动注音**（tencent 981k 条）：
  - 字表合并：8105 权重优先，41448 补充生僻字
  - 默认取每字最高频读音
  - 多音扩展：词长 ≤4 且含多音字时，用每字前 2 读音做笛卡尔积，最多保留 4 个变体，权重 ×0.6
  - 无法注音（含字表外字符）的词直接丢弃并计数
- **注音准确率验证**：用 base/ext 自带注音当标准答案，随机抽 5,000 词跑自动注音，报告 top-1 准确率。低于 95% 就先修算法再继续（这是唯一能提前量化的质量指标）
- 索引生成：
  - 全拼精确键（全部词）
  - 简拼键：全部词（2～8 字母），不再限制前 2.5 万
  - 混拼键（首全尾简 / 首简尾全）：仅前 10 万高频词
  - 每键候选上限 12 → 16
- 噪声过滤：含非汉字字符、长度 >8、纯数字/符号、含字表外生僻字的 tencent 词
- 输出分层：
  - `xy_embedded.bin`（内置档）
  - `xy_ext.bin`（可选扩展档，格式与现有 `XYDICT01` 一致）
- 构建结束打印统计：词数、键数、各库贡献、丢弃数、文件大小

### Phase 2：运行期改造（2～3 天）

1. **双词典层**：`init_lm` 现在加载外部词典会覆盖内置词典（`load_dict_file_locked` 是单实例）。改成 `g_dict_core_*` + `g_dict_ext_*` 两层，查询时先 core 后 ext，按权重合并去重。
2. **前缀检索**（这是"拼音索引"最实质的升级）：
   - 现状：`exactMatchSearch` 只认整串拼音，用户敲 `beij` 时词库一个候选都给不出
   - 改为 Darts `traverse` 定位前缀节点 + 有界 DFS（≤4096 节点、≤2000 条），按权重取前 N
   - 仅在输入长度 ≥2 且精确匹配候选不足时启用，避免每键都扫
3. **候选合并**：`query_dict_pinyin` 与 `lookup_dict_matches_for_span` 同时读两层，保持"真实词频 > 弱先验"的排序
4. **内存**：所有数据 mmap（内置走 `.so` 的 `.rodata`，扩展档走文件），冷启动只按页加载；`word_trie` 只保留前 30 万词（该表只用于重排先验，长尾词给 0 分即可），可省 10MB+

### Phase 3：词库管理 UI（1 天，可选）

- 「扩展词库」入口：导入/启用/停用/删除，显示词条数与版本
- 如果决定规避 GPL-3 分发问题：APK 只保留 A 档精简词库，用户自己导入 rime-ice 生成的扩展档
- 隐私/权限：扩展档放在模块 APK 的 `assets`（`noCompress` 存储，可 `openFd` 直接 mmap），避免输入法进程读不到应用私有目录的问题

### Phase 4：验证（1 天）

| 项目 | 标准 |
|---|---|
| 覆盖率 | 从 ext/tencent 抽 1,000 词，全拼输入，前 3 候选命中 ≥95% |
| 注音准确率 | base/ext 标准答案上 top-1 ≥95% |
| 回归 | dz 快捷短语、@上文 联想、整句解码、点击上屏清空候选栏全部通过 |
| 性能 | 单键输入延迟 P95 增量 <5ms；输入法进程 RSS 增量 <60MB |
| 稳定性 | 无崩溃/ANR，冷启动可接受 |

## 四、风险清单

1. **GPL-3.0**：内嵌 rime-ice 词库分发会传染；公开 Release 前必须处理（开源、换数据源、或改用户导入）。
2. **多音字注音错误**：42% 的 tencent 词涉及多音字；靠多读音扩展 + 抽样验证兜底，无法做到 100%。
3. **长尾噪声**：tencent 含大量 `〇〇八` 这类词；过滤规则要在构建期可调。
4. **包体**：B 档 `xy_embedded.bin` 约 45MB（含 LM 与词先验），APK 预计 60～70MB；需确认你接受。
5. **前缀检索性能**：有界 DFS 的节点上限要实测调参。
6. **`lastCommittedWord` 之类的既有逻辑**：词库变大后，去重与提权规则要回归一遍（上一轮 dz 交替问题就是这类）。

## 五、建议的落地顺序

1. 我先扩展构建工具，产出 **A 档**和 **B 档**两个 bin，跑注音准确率与体积报告（不动运行期代码，可回滚）
2. 你对比覆盖率和包体，选一档
3. 再接运行期双词典层 + 前缀检索
4. 最后做词库管理 UI 和 GPL 方案确认

第 1 步只改 `tools/`，不影响现有 APK，是最安全的第一步。
